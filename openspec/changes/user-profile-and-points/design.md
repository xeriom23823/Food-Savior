## Context

點數規則（加權、每日上限）已經在 `design-system-redesign` 做完並實機驗過，但只寫進每一筆 `UsedFoodItem.affectFoodPoint`，沒有任何彙總呈現。用戶分頁同時是五個分頁裡最空的一個。這個 change 把兩件事合起來解決：用既有資料算出「成績」，放進用戶頁。

## Goals / Non-Goals

- Goals：點數看得到且有進展感；用戶頁有被點開的理由；補齊帳號功能的實質缺口（改名、重設密碼、刪帳號）；登入頁不再是重製前的舊樣子。
- Non-Goals：訪客模式、排行榜、點數兌換、頭像上傳、自動同步。

## Decisions

### D1. 成績全部由既有紀錄推導，不新增持久化欄位

- `FoodPointsSummary.from(items, now:)` 是純函式，輸入 `List<UsedFoodItem>`、輸出總分／本週／等級／天數／里程碑。
- 理由：點數已經逐筆存在 `affectFoodPoint`，再存一份累計值就會有兩個真相，而且還原備份時必須重算。推導沒有同步問題。
- 取捨：紀錄很多時每次都要掃一遍。實測量級（家庭使用，一年幾百筆）完全不是問題；真的變慢再加快取。

### D2. 「連續天數」= 距離上次浪費的天數，不是登入連續天數

- 定義：今天減去最後一筆浪費紀錄的日期。沒有任何浪費紀錄時，從第一筆紀錄算起；完全沒有紀錄時為 null（不顯示）。
- 理由：登入 streak 會懲罰「那幾天沒開 App」，但沒開 App 不代表浪費了東西。這個定義只陳述事實——距離上次浪費過了幾天——斷掉時也只是回到 0，不會有「我的紀錄毀了」的挫折。
- 捨棄：連續有記錄天數（鼓勵打卡而不是鼓勵不浪費）。

### D3. 五個等級，門檻線性放大

| 等級 | 門檻 | key |
|---|---|---|
| 1 | 0 | `levelNoviceName` |
| 2 | 50 | `levelKeeperName` |
| 3 | 150 | `levelSaverName` |
| 4 | 350 | `levelGuardianName` |
| 5 | 700 | `levelMasterName` |

- 以「正常食用 +2」估算：每天吃掉 2〜3 樣東西約 5 分，50 分約兩週、700 分約半年。半年到頂對一個家用工具是合理的節奏。
- 等級只看**累計總分**，且總分不會因為浪費而倒退到負的門檻——`level` 取 `max(totalPoints, 0)` 對照門檻，避免「降級」的羞辱感。但**總分本身照實顯示**（可以是負的），因為那是誠實的數字。

### D4. 里程碑是一次性成就，未達成也要看得見

- 六個：第一筆紀錄、救回 10 項即期、累計 100 點、連續 7 天沒浪費、連續 30 天沒浪費、累計 500 點。
- 未達成的以灰階 + 達成條件文字呈現，不隱藏。看得到目標才有方向；藏起來只會讓人以為沒東西可解鎖。
- 里程碑同樣是推導的，不存狀態，所以刪除紀錄後會退回未達成——這是誠實的結果。

### D5. `AuthenticationRepository.user` 改為可手動推播

- 問題：`updateDisplayName` 只改 Firebase 的 profile，`authStateChanges()` 不會發射，畫面上的名字不會更新。
- 作法：`user` 改為 `authStateChanges()` 與一個內部 `StreamController` 的合流；`updateDisplayName` 完成後 `reload()` 再推一次目前的使用者。
- 風險：這條串流是路由的依據（`AppBloc` 靠它決定登入狀態），改壞會讓人卡在登入頁 → 以 repository 測試與既有 `app_bloc` 測試鎖定。
- 捨棄：改用 `idTokenChanges()`（profile 更新不一定換 token，不可靠）。

### D6. 刪除帳號：只負責刪帳號，不負責刪本機資料

- Firebase 的 `delete()` 在近期未登入時會丟 `requires-recent-login`，對應到一個明確的失敗原因，UI 顯示「請重新登入後再試」。
- 刪帳號**不會**清掉本機 Hive 資料：那是使用者的食物清單，跟帳號是兩件事（目前帳號只用於雲端備份）。確認對話框要把這件事寫清楚，不要讓人以為資料一起沒了。

### D7. 用戶頁在沒有紀錄時不顯示成績

- 全新使用者看到「0 分、等級 1、0 個里程碑」只會覺得自己很失敗。沒有任何使用紀錄時，成績區換成 `EmptyState` + 「去記第一樣食物」。
- 有紀錄之後才出現等級卡與里程碑。

### D8. 登入頁的錯誤訊息固定在表單上方，不用 SnackBar 蓋住按鈕

- 原本用白底 SnackBar（深色模式刺眼，而且會蓋住登入按鈕）。改為表單上方的固定錯誤區塊，錯誤與造成錯誤的欄位在同一個視線範圍內。
- `AppSnackBar` 仍用於「重設信已寄出」這類成功回饋。

## Risks / Trade-offs

- **推導成本**：每次進用戶頁都要掃全部紀錄。可接受（見 D1），若之後紀錄破萬再考慮快取。
- **里程碑會退回**：刪紀錄會讓已達成的里程碑消失。誠實但可能意外；確認刪除時不特別提醒（過度提示更煩）。
- **等級門檻是猜的**：沒有真實使用資料前，門檻只能估。寫成常數集中一處，之後要調很容易。
- **與 Codex 並行**：Codex 正在 `lib/widgets/`、`lib/theme/` 做圖示與插畫整合。本 change 盡量不動那兩個目錄，新元件放 `lib/pages/user/`。

## Migration Plan

1. 純 Dart 的 `FoodPointsSummary` + 測試（不接 UI）。
2. `AuthenticationRepository` 的三個新方法 + 可推播串流 + 測試。
3. 用戶頁重製（成績區 → 帳號區）。
4. 登入／註冊頁重製。
5. l10n、widget test、實機。
