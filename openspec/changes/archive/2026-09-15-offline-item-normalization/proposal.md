## Why

`scan-einvoice-import` 把「掃發票 → 草稿 → 匯入」的管線接起來了，但**命中率由對照表的規模決定，而目前只有 35 筆、96 個關鍵字**。沒命中的品項會退成 `others` + 期限未知，使用者還是得逐列改類型與期限——省下的只有數量與金額。快速新增走的是同一條路徑，一樣受限。

實測目前的弱點（同一份對照表，同一個比對函式）：

| POS 品名 | 現在的結果 | 應該是 |
|---|---|---|
| `牛奶糖` | `eggAndMilk` | `snack` |
| `沙拉油` | 未命中 | `others`／調味 |
| `花生醬` | 未命中 | `others` |
| `雞蛋豆腐` | `eggAndMilk` | `cookedFood` |

「牛奶糖被當成牛奶」不是演算法壞掉——`FoodSuggestionEngine.presetFor()` 的「最長命中關鍵字優先」本來就能處理，**前提是字典裡有「牛奶糖」這一條**。所以這主要是資料問題，不是邏輯問題。

本 change 要驗證的假設：**把對照表做大並建立可量測的基準，命中率能到「大多數品項不必手改」的水準。**

同樣重要的是：目前沒有任何方式知道命中率是多少、改動之後是變好還是變壞。本 change 把它變成一個**有門檻、會擋回歸的數字**。

### 為什麼叫 offline

這個 change 一開始叫 `ai-item-normalization`，實作完成後改名。LLM **只在開發期**用來產生字典內容，產出是一份 commit 進版控的 JSON；**執行期沒有任何 AI、沒有後端、沒有網路請求、沒有 API 成本**。名字裡帶「AI」會讓日後讀 archive 的人以為這裡有模型呼叫，所以改掉。

這延續 design-system-redesign D15 已經做過的決定（`food_preset.dart` 的註解寫得很清楚：「完全離線、可單元測試、沒有 API 成本；使用者選擇不走 AI 猜測」）。

## What Changes

### A. 命中率基準（新，本 change 的核心）

- 新增 `test/fixtures/product_names/benchmark.json`：一組真實風格的 POS 品名，每筆人工標註期望的 `type`（以及可判定時的 `unit`）。
- 新增基準測試：計算命中率並斷言**不得低於設定門檻**。門檻寫成常數並在測試檔註明當時的實測值。
- 效果：以後任何人動對照表或比對邏輯，測試會證明有進步，也會擋住回歸。沒有這個，「擴充字典」就只是感覺。

### B. 擴充內建對照表（資料）

- `assets/data/food_presets.json` 從 35 筆擴充到約 200 筆，涵蓋台灣常見生鮮與加工食品。
- **重點是消歧條目**：凡是「短詞是另一類的長詞前綴」的情況都要補進去（牛奶／牛奶糖、蛋／蛋糕／雞蛋豆腐、沙拉／沙拉油、花生／花生醬、奶油／鮮奶油）。最長命中優先本來就會處理，只要資料齊全。
- 每一筆都要有保存天數（冷藏／冷凍／常溫）與合理的預設單位。

### C. 擴充雜訊詞表（資料）

- `assets/data/product_noise_terms.json` 補齊更多品牌、通路、促銷與溫層用語。
- 新增一條規則：雜訊詞**不得是任何對照表關鍵字的子字串**，否則會把食物名稱本身剝掉。這一條要有測試強制。

### D. 比對規則明確化（小幅邏輯調整）

- 目前若兩筆 preset 的最長命中長度相同，結果取決於 JSON 的排列順序——這是未定義行為。明確定義平手規則並測試。
- 比對前先建索引，避免每次匯入都對 200 筆 × 每筆數個關鍵字重複掃描。

### 範圍上限

兩個 JSON 資料檔、一個基準 fixture、`FoodSuggestionEngine.presetFor()` 的比對規則。**不新增套件、不新增畫面、不改 Bloc 事件與狀態、不改 Hive schema、不呼叫任何網路服務。**

### 非目標

- **不做執行期的 LLM 呼叫**，不做 Cloud Functions，不做任何後端。
- 不做群眾外包詞庫（使用者修正回寫共享字典）——那需要 Firestore 與濫用防護，是獨立 change。
- 不做商品條碼查詢（Open Food Facts）。
- 不追求 100% 命中率。目標是把「大多數常見品項免手改」做到，剩下的靠 `needsReview` 標示讓使用者快速處理。
- 不改動使用者歷史模板優先於內建對照表的順序（design D17 已定）。

## Capabilities

### New Capabilities

- `item-normalization`：由食物名稱推導類型、單位與建議保存期限的行為契約——對照表的結構與必要欄位、最長命中與平手規則、雜訊詞與關鍵字不得衝突的約束、未命中時的退路，以及命中率基準的門檻要求。

### Modified Capabilities

無。本 change 只讓既有行為更準，不改變任何已定義的可觀察契約：未命中仍退回 `others` + 期限未知，模板仍優先於對照表。

## Impact

- **Code**：`lib/models/food_suggestion.dart`（`presetFor` 的平手規則與索引）、`assets/data/food_presets.json`（資料）、`assets/data/product_noise_terms.json`（資料）。
- **資料模型**：**不改 Hive schema、不改 `FoodPreset` 的欄位定義**。既有的 `FoodPreset.fromJson` 就能讀新資料；未知的 `type`／`unit` 字串本來就會退回 `others`／`piece`，所以資料寫錯不會讓 App 起不來。
- **Bloc 狀態**：不改。
- **l10n**：不新增字串（對照表的關鍵字是比對用的資料，不是使用者可見文字）。
- **平台權限**：不變。
- **Dependencies**：不新增。
- **Tests**：新增基準測試與雜訊詞衝突測試；既有的 `food_suggestion` 與 `invoice_draft_mapper` 測試必須維持全綠——它們鎖的是行為契約，資料變大不該讓它們壞掉。
- **Risk**：擴充字典可能讓某些原本正確的品名變成誤判（新增的短關鍵字誤命中）。以基準測試防守：命中率不得下降，且既有測試不得變紅。
