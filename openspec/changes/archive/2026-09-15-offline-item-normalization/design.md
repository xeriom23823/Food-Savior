## Context

動機見 proposal.md「Why」。影響作法的現況：

- **推導邏輯已經存在且正確**。`FoodSuggestionEngine.presetFor()`（`lib/models/food_suggestion.dart`）已經實作「最長命中關鍵字優先」。實測顯示的誤判（牛奶糖 → 蛋奶類）是因為字典裡沒有「牛奶糖」，不是因為演算法錯。
- **兩條路徑共用同一個推導**：食物分頁的一行快速新增、以及 `scan-einvoice-import` 的草稿產生。把字典做大，兩邊同時變準——這正是 `scan-einvoice-import` 的 D6 刻意重用既有引擎的原因。
- **資料契約已固定**。`FoodPreset.fromJson` 對未知的 `type`／`unit` 字串已有退路（`others`／`piece`），所以資料寫錯不會讓 App 起不來，但也代表**錯字會安靜地變成 `others`**——需要測試把關。
- **雜訊詞表是本 change 引入的新風險**。`scan-einvoice-import` 加了 `product_noise_terms.json`，剝除是無條件 `replaceAll`。詞表一大，就可能剝掉食物名稱本身。
- **目前沒有任何命中率的量測**。

## Goals / Non-Goals

**Goals:**

- 把「命中率」變成一個**有門檻、會擋回歸的數字**，而不是感覺。
- 擴充字典時不破壞既有行為：既有測試全綠、基準命中率只升不降。
- 保持執行期零 AI、零後端、零網路。

**Non-Goals:**

- 不追求 100% 命中率。長尾靠 `needsReview` 標示 + 使用者一次點擊修正。
- 不做詞形變化、拼音、模糊比對（編輯距離）。中文品名的主要問題是雜訊與消歧，不是拼錯。
- 不為效能重寫推導。200 筆的規模下，建索引就夠。

## Decisions

### D1：先做基準，再擴字典

順序刻意如此。沒有基準就無從判斷擴充是否真的有幫助，也無從發現「新增的短關鍵字讓原本正確的品項變成誤判」這種回歸。

`test/fixtures/product_names/benchmark.json`：

```json
[
  {"name": "統一AB優酪乳400ML特價", "type": "eggAndMilk"},
  {"name": "牛奶糖", "type": "snack"},
  ...
]
```

樣本 SHALL 走**完整管線**（`ProductNameCleaner` → `FoodSuggestionEngine`），不是只測比對函式——否則量到的不是使用者實際會遇到的命中率。

**門檻寫成測試檔裡的常數**，並在註解記下當時的實測值。門檻要比實測值略低一點（留一點雜訊空間），但任何實質下降都要讓測試變紅。

### D2：擴字典的內容由開發期的 LLM 產生，產出進版控

我（Claude Code）在開發期直接產生 JSON 內容，commit 進 repo。執行期只是讀一個 asset 檔。

這是整個「要不要用 LLM」討論的落點：**LLM 的價值在把這份字典寫出來，不在每次掃描時呼叫它**。一次性產生的東西不該變成每次請求的成本、延遲與隱私面。

字典內容的取捨：
- 只收**台灣零售常見**的品項。收一堆沒人買的東西只會增加誤命中的機會。
- 保存天數取**保守值**（偏短）。提醒早一點響沒關係，晚了東西就壞了。
- 每一筆都要能回答「這個關鍵字會不會誤命中別的東西」。

### D3：消歧靠資料，不靠新的排除機制

「牛奶糖被當成牛奶」的修法有兩種：加一套「排除詞」機制，或把「牛奶糖」當成 `snack` 的關鍵字加進字典。

選後者。最長命中優先**本來就是**消歧機制，只要資料齊全就會運作；加排除詞等於在同一件事上疊第二套規則，兩套規則會互相打架。

要補的消歧對分兩種，**不要混為一談**——基準測試對兩者的斷言不同：

**(a) 類型不同**：推導出的 `FoodItemType` 必須不一樣。

| 短詞 | 長詞 | 差別 |
|---|---|---|
| 牛奶 | 牛奶糖 | `eggAndMilk` vs `snack` |
| 蛋 | 蛋糕 | `eggAndMilk` vs `bread` |
| 蛋 | 雞蛋豆腐 | `eggAndMilk` vs `cookedFood` |
| 沙拉 | 沙拉油 | `vegetable` vs `others` |
| 花生 | 花生醬 | `snack` vs `others` |

**(b) 類型相同但保存期限差很多**：型別斷言抓不到，要斷言天數。

| 短詞 | 長詞 | 差別 |
|---|---|---|
| 奶油 | 鮮奶油 | 都是 `eggAndMilk`，但鮮奶油開封後只有幾天 |
| 米 | 米酒 | 都是 `others`，但米可放一年、米酒開封後另計 |

一開始把這兩種混在同一張表，導致基準測試對 `奶油／鮮奶油` 斷言「類型必須不同」而失敗——**測試抓到的是規格自己的錯**，不是實作的錯。

### D4：命中選擇改為「最靠近字尾優先」（實作時發現原規則不對）

原本只打算修平手規則。基準測試跑出來之後發現更根本的問題：**「最長命中優先」對中文是錯的規則**。

擴充字典後唯一漏掉的樣本是「巧克力蛋糕」被歸成零食——因為「巧克力」（3 字）比「蛋糕」（2 字）長。但中文複合詞的**中心語在字尾**：巧克力蛋糕是蛋糕、牛奶糖是糖、鮪魚罐頭是罐頭、蘋果汁是汁。只看長度必然會選到修飾語。

改成三層規則：

1. **結束位置最靠近字尾者勝**（主規則，符合中文構詞）
2. 結束位置相同時，**較長者勝**（「雞蛋豆腐」勝過「豆腐」）
3. 再相同時，**字典序較小者勝**

第 3 條實務上碰不到——結束位置與長度都相同就是同一個子字串——但留著讓結果**與對照表在檔案裡的排列順序無關**。原本的迴圈是「嚴格大於才換人」，同分時先出現的贏，等於把推導結果綁在 JSON 的排列上；重新排序資料檔就可能改變行為，這種 bug 極難追。資料健檢另外強制「同一個關鍵字不得出現在兩筆」，把這個退化情況從資料面也堵掉。

改完之後那份基準從 98.4% 升到 100%，而且既有的「牛奶糖不會被當成牛奶」測試照樣通過——新規則涵蓋了舊規則想處理的案例。

### D5：不建索引（實作時推翻了原本的計畫）

原本打算在建構 `FoodSuggestionEngine` 時預先算好排序過的關鍵字索引。實際讀了呼叫端之後放棄，理由有二，都是硬性的：

1. **`FoodSuggestionEngine` 與 `FoodPreset` 都有 `const` 用法**（`test/models/food_suggestion_test.dart`）。在建構子裡算東西就不能是 `const`，會連帶改到既有測試——為了一個沒量到的效能問題去動行為契約的測試，不划算。
2. **`FoodItemListBloc.suggestionEngine` 是 getter，每次存取都 new 一個新的 engine**（模板要每次重新從歷史推導）。索引建在建構子裡會變成**每次存取都重算**，比現在更慢。

重新估算實際成本：200 筆 × 平均 4 個關鍵字 = 每次 `presetFor` 約 800 次子字串比對，都是短字串，在毫秒以下。一張 10 品項的發票也就 8000 次，使用者完全感覺不到。**這是一個想像出來的效能問題。**

真正的浪費是每次比對都對每個關鍵字重跑 `normalizeFoodName()`（配置 StringBuffer + 逐 rune 走訪）。但要消除它就得把正規化結果存進 `FoodPreset`，同樣會破壞 `const`。既然總成本本來就在毫秒以下，**不值得為此改資料模型**。

保留現況的 O(n×m) 掃描。本 change 只改 D4 的平手規則。

### D6：雜訊詞與關鍵字的衝突用測試擋，不用執行期檢查

「雜訊詞不得包含任何對照表關鍵字」這條約束，在執行期檢查只會拖慢啟動且無法修正。放在測試裡：兩份 asset 都讀進來，交叉比對，衝突就讓測試失敗並印出是哪一對。

這樣加詞的人會在 CI 就知道自己剝掉了食物名稱。

## Risks / Trade-offs

- **擴充字典造成新的誤命中** → 這是本 change 最主要的風險，也正是 D1 先做基準的原因。基準樣本必須包含新加關鍵字附近的案例。
- **基準樣本本身有偏誤**（我造的樣本剛好是字典擅長的） → 樣本要以真實發票與賣場品名的**寫法**為準（含品牌、促銷、規格、全形），而不是乾淨的食物名。未來拿到真實發票字串時應補進樣本。
- **人工標註可能有爭議**（「蛋糕」算 bread 還是 snack？） → 標註以 App 內既有的類型定義為準，有爭議的直接不收進基準，避免用一個主觀判斷去卡未來的改動。
- **保守的保存天數讓提醒過早** → 寧可早。過期提醒是 roadmap 的下一項，屆時可依使用者實際「還沒壞」的回饋調整；資料在 JSON 裡，調整成本低。
- **字典永遠不夠大** → 接受。目標是常見品項免手改，不是全覆蓋；`needsReview` 讓長尾一眼可見。

## Migration Plan

無資料遷移：`FoodPreset` 的欄位定義不變，既有 `fromJson` 直接讀新資料。

- **上線**：改 JSON → 跑基準測試 → 跑全部測試。
- **回滾**：把兩個 JSON 檔還原即可，沒有任何程式碼依賴新資料的存在。
